# StoryBuilder Application Audit
Date: October 21, 2026
Audited ref: `main` at `96b29b94775029e64eccee07dfd816e0dc96ffd9`
Scope: static review of the GitHub source tree, key writer/revision/state/package/sync modules, tests, workflow definitions, and latest CI results. No application code or novel prose was changed. The desktop app and local GGUF model were not run in this audit, so findings about live model behavior are separated from source-level findings.

## Executive assessment

**StoryBuilder is not a write-off.** It has substantial safety and continuity infrastructure, broad regression tests, and both configured CI workflows passed on the audited `main` commit. The repeated Focused Change failure is a real design weakness that current tests do not cover. Fix that narrow path first; do not rewrite the application wholesale.

## What appears sound in source and tests

- **Writer lifecycle and recovery:** generation runs in a worker thread; status/buttons track busy state; generated drafts are tied to their originating chapter/scene and starting-state snapshot; failed regeneration is designed to preserve the old draft; failed focused edits leave visible prose unchanged.
- **Acceptance and story data protection:** accepting prose checks its chapter/scene identity and starting state; existing section replacement asks for confirmation; accepted prose is separated from state analysis and application. State proposals are reviewed before application, merged as patches, validated, and snapshotted before advancing the scene pointer.
- **Continuity/state layer:** current state and historical manuscript are separated; historical retrieval only considers earlier accepted sections and labels sources; context budgeting prioritizes key current-scene facts; character knowledge is handled as a delta instead of replacing the complete ledger. State manager validation has many targeted regression tests.
- **Package and sync safety:** package discovery is constrained to supported paths; local save and novel-repository sync are distinct; sync code has explicit error handling for Git failures/conflicts. The README correctly warns that prompt traces can contain unpublished story text and describes trace capture as opt-in.
- **Test/CI baseline:** there are focused tests for exact-patch application, scene completion, context budgeting, state validation, package paths, manuscript candidate selection, prompt tracing, and workflow safety. On the audited commit, both [StoryBuilder checks](https://github.com/tony21675/StoryBuilder/actions/runs/39557373301) and [StoryBuilder tests](https://github.com/tony21675/StoryBuilder/actions/runs/39557373271) completed successfully. This is automated test evidence, not proof that the local model produces good prose.

## Findings ranked by priority

### P0: Focused Change depends on the model copying its own edit target

Files: `builder/focused_revision.py`, `storybuilder.py`, `tests/test_focused_revision.py`.

The current design sends the entire draft plus the request to the local model and asks it to return `target_text` copied verbatim from the draft and `replacement_text`. The app then rejects the patch unless that target can be found exactly once. Whitespace is normalized flexibly, but punctuation, spelling, quotation/apostrophe style, and other characters still must match. This is intentionally conservative, but it makes a smaller local model responsible for both understanding the change and accurately quoting a possibly long passage. The live test has now failed repeatedly at this target-matching step, despite increasingly narrow instructions.

The retry loop has a second weakness: `engine.reset_context(...)` runs once before the two-attempt loop, so attempt two is sent into the same interactive model conversation after attempt one's full prompt and response. The second prompt also includes the previous response. That can inflate/reinforce the context rather than giving the retry a clean attempt. The failure UI reports the validation error but does not show the rejected target or raw model patch for diagnosis unless an appropriate prompt trace was captured.

There is also a task-configuration mismatch worth fixing: focused revision restarts the shared WriterEngine, whose `start()` does not set task-specific temperature/top-k/top-p, so the JSON patch request uses llama.cpp defaults. Some standalone contract/validator paths set explicit sampling parameters, but this focused-revision path does not. This is a plausible consistency risk, not a proven sole cause of the observed target mismatch.

Current unit tests mostly use short, artificial snippets. They verify safe replacement and rejection, but do not cover long realistic prose, curly/straight quote drift, model target-copy failure under long context, retry context lifecycle, or sampling configuration. That gap explains why CI can pass while the reported real-model workflow still fails.

**Recommended repair, after approval:** make selection-aware revision the primary path. Let the author select the exact passage in the Writer text widget; pass that source substring directly to the model and ask for replacement text only. The application should verify that the selected source still matches the editor at the captured offsets before applying the replacement, and preserve every character outside that span. Keep a guarded fallback for unselected requests only if it can be diagnosed clearly. Reset the model conversation between retry attempts. Add tests for selection offsets, text changed during generation, punctuation/quote variants, multi-paragraph selections, a realistic long draft, retry reset behavior, and exact preservation outside the selected span. Do not implement a fuzzy replacement that could silently edit the wrong passage.

### P1: Content review is model-assisted, not a guarantee

Files: `builder/scene_contract.py`, `builder/scene_completion.py`, `storybuilder.py`.

The generation pipeline includes a semantic scene-coverage check and a five-category integrity audit for timeline/order, character presence/knowledge, physical continuity, unsupported consequential details, and scope/hard-stop. Ambiguous audit output is designed to preserve the original draft rather than assert a pass, and verified conflicts can trigger one retry. This is good defensive design.

However, the current live draft still overshot the author’s explicit endpoint by moving into specific task assignments and discreet-surveillance planning. The audit did not prevent that outcome in the run the author reviewed. The available evidence does not establish whether the model returned a false “clear,” which source context it received, or whether a warning was shown; raw live audit output was not supplied. Treat this as an observed effectiveness gap, not proof of a particular line of code being broken.

**Recommended improvement:** expose the review outcome in the Writer UI after generation, including clear / conflict / uncertain and the key evidence/reason, instead of leaving the author to infer that the checker caught everything. Add a regression scenario with the Chapter 3 Scene 3-style boundary: “rough framework begins to take shape” must not permit detailed role assignments or surveillance plans. Keep final acceptance the author’s choice unless a future acceptance gate is explicitly discussed.

### P1: Main UI module is a large maintenance hotspot

File: `storybuilder.py` (roughly 418 KB in the audited tree).

The app coordinates many tabs, thread lifecycle, editor content, state transitions, saves, and sync logic in one large Tkinter class/module. Targeted helper modules are already separated, but the central UI file remains difficult to inspect and makes regressions/race conditions harder to isolate.

**Recommended approach:** do not conduct a sweeping refactor during this repair. First fix and test Focused Change. Then, if agreed, move one cohesive workflow at a time into small UI/controller modules with unchanged behavior and regression tests.

### P2: CI runs the same unit suite in two separate workflows

Files: `.github/workflows/storybuilder-checks.yml`, `.github/workflows/storybuilder-tests.yml`.

Both run compileall and unittest discovery on pushes to `main` and pull requests, using Python 3.11 and 3.12 respectively. Both passed on the audited commit. Testing both Python versions is useful; maintaining duplicate workflow definitions is unnecessary and can make status reporting noisier.

**Possible cleanup:** consolidate to one workflow with a Python-version matrix, preserving coverage of both 3.11 and 3.12. This is housekeeping, not the immediate repair.

### P2: Repository tree contains an unexplained nested Git link

The root tree includes a `StoryBuilder` path recorded as a Git submodule/gitlink (mode `160000`), but no `.gitmodules` file appears in the tree. This may be a leftover nested checkout or an intentional pointer; the reason is not documented. Do not delete it blindly. Inspect local status and history first, then decide whether it belongs.

### P2: Current `main` has no branch protection

The GitHub branch metadata reports `main` as unprotected, with no required status checks. The user's desired main-only workflow can still be preserved, but future direct pushes can bypass a required-check gate. Whether to add protection is an operational choice; do not change repository settings automatically, especially while using direct-to-main commits.

## Recommended repair order

1. **Pause live Focused Change retries.** Reproduce its failure from source and make an approved design decision on passage selection.
2. **Repair the selected-passage edit path** with strict source-span preservation and fresh retry context; add realistic unit tests.
3. **Verify locally with the current model** using a disposable novel copy and a long multi-paragraph selection. Confirm the prose outside the selection is byte-for-byte unchanged and failed edits leave the draft unchanged.
4. **Improve visibility of scene audit outcomes** and add a test that asserts the explicit scene endpoint/hard-stop case is flagged by the live review procedure. Do this after the editing fix, one scoped change at a time.
5. Tackle the monolith, duplicate workflows, gitlink, and branch protection separately, only after discussion.

## Additional priority: natural narrative flow

The Chapter 1/Chapter 2 comparison surfaced a separate quality concern: Chapter 2 sometimes repeats emotional distress and reassurance rather than letting each beat develop. This is an observed manuscript pattern, not proof of a single prompt cause. The creative-first prompt is already merged, so investigate the complete runtime prompt/context and available traces before changing it. Preserve explicit canon, character knowledge, required beats, and hard stops; avoid duplicating soft craft preferences across context blocks. Use a controlled disposable comparison and evaluate prose quality alongside continuity and scope. See [STORY_FLOW_REPAIR_PLAN.md](STORY_FLOW_REPAIR_PLAN.md). No code or manuscript changes are included in this audit update.


The source-level follow-up further localized the likely simplification target. `SceneContract.writer_prompt_context` repeats some general guidance already present in the static Writer prompt and scene-boundary brief, especially scene intent, agency, scope, event provenance, and clue boundaries. However, it also carries unique per-scene requirements and the hard stop. The next experiment should classify unique anchors versus repeated general craft guidance, then change only the latter if testing supports it. See [STORY_FLOW_REPAIR_PLAN.md](STORY_FLOW_REPAIR_PLAN.md).


## October 25, 2026: text selection and copy-control audit

The app already installs right-click context menus and Ctrl+A/Ctrl+C handlers for text widgets present at startup. The remaining gap is dynamically created popup content: validator findings, diagnostics, and scene-flow reports are built after that startup scan. Install shared keyboard/context-menu handling when those popup fields are created. Include ordinary entries, spinboxes, and comboboxes in app-wide widget discovery.

User-approved UI rule: no dedicated copy-only buttons. Text fields should allow Ctrl+A then Ctrl+C. A Full Scene Draft read-only tab in the modal validator review keeps the complete prose available without closing the review. Diagnostic and scene-flow text should remain selectable. Right-click Copy/Select All remains a secondary convenience without toolbar clutter.

Remote CI and live GUI verification are pending. No novel package, accepted prose, or saved story state is changed by this UI work.
